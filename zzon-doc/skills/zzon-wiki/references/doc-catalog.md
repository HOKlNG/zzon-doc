# 문서 카탈로그 (템플릿)

> **이 카탈로그는 템플릿이다.** 실제 트리는 인터뷰+코드 스캔으로 프로젝트에 맞게 **인스턴스화해 wiki.json에 기록**한다 — build-wiki는 wiki.json만 읽는다.
> SI 개발 프로세스 12단계(00~11) 기반. 프로젝트 고유명(제품·클라우드 서비스명)은 여기 없다 — 인스턴스화할 때 채운다.

## 티어 (노드 태그 — 승격은 노드 추가일 뿐)

| tier | 이름 | 규모 | 대상 |
|---|---|---|---|
| 1 | **라이트** | ~15장 | "이미 구현된 프로젝트 역문서화"의 기본값. 개요+아키텍처+데이터+API+퀵스타트+운영 핵심 |
| 2 | **표준** | ~35장 | 팀 온보딩·유지보수가 목적. 라이트 + 요구/기획/규약/운영 상세 |
| 3 | **풀 SI** | ~90장 | 발주·감리·계약 산출물이 필요할 때만 |

- **todo는 wiki.json 엔트리로만** — 빈 md 파일을 만들지 않는다.
- `dynamic` 표시 노드: children을 카탈로그가 아니라 **코드 스캔 결과**(실제 도메인·테이블·API)로 생성한다.
- 섹션 전체가 해당 없으면 통째로 제외(`interview.excludedSections`에 사유와 함께). 문서 하나만 해당 없으면 `status: "na"` + `naReason`.

## 인스턴스화 절차 (스킬이 wiki.json을 만들 때)

1. 승인된 티어의 노드만 트리에 넣는다 (tier 태그는 유지 — 나중 승격 대비).
2. `dynamic` 노드는 코드 스캔 결과로 children을 만든다 (예: api-spec → 실제 도메인 Orders/Catalog…).
3. 프로젝트에 없는 개념은 넣지 않거나 na 처리한다 — **카탈로그를 그대로 복사하지 마라.**
4. 각 노드의 summary를 프로젝트 문맥으로 다시 쓴다 (카탈로그 문구 복붙 금지).
5. 섹션 제외는 `interview.excludedSections`에 사유와 함께 기록한다.
6. **섹션 `code`는 포함된 섹션에 카탈로그 순서대로 `"00"`부터 연속 재부여한다.** 카탈로그의 번호는 템플릿 식별용일 뿐 — 제외한 섹션의 번호를 비워둔 채 `00, 05, 06…`으로 만들지 마라(빌드가 경고한다). 나중에 섹션을 승격·추가하면 카탈로그 순서 자리에 끼우고 code를 전체 재부여한다 — 문서 참조는 `path` 기준이라 code 변경은 안전하다.
