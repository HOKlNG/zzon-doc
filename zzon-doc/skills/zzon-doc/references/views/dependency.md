# 모듈 의존성 (`docKind: "dependency"`) — 기계 생성

**질문**: 모듈(디렉터리·패키지)이 서로 무엇에 의존하나. 순환이 있나. 레이어 규칙을 어기나.
**독자**: 개발자.
**등급**: 집계한 모듈 수가 정한다(4~20이면 T2).

> **이 뷰는 손으로 저작하지 않는다.** import를 눈으로 훑으면 빠지거나 지어낸다.
> 생성기가 import 문을 읽고 모듈 단위로 집계해서 DSL을 쓴다. 같은 코드면 같은 그림이 나온다.

## 생성

```bash
node $Z/skills/zzon-doc/scripts/scan-deps.mjs <프로젝트 루트> --out <docsDir>/terra/deps.ts --slug deps
#   --src <소스 루트>   기본: src·app·lib·packages 중 코드가 가장 많은 곳. 모노레포는 앱 단위로 지정(--src apps/api)
#   --depth N           집계 깊이. 기본: 모듈 4~20(T2)에 드는 가장 얕은 깊이
#   --types             import type도 의존으로 센다(기본은 런타임 의존만)
#   --json              그리지 않고 집계 결과만 본다
```

- **지원 언어**: JS/TS(상대 경로·패키지별 tsconfig paths·워크스페이스 패키지 이름), Python(절대·상대 import), Go(go.mod 모듈 경로), Java/Kotlin(package 선언).
- 테스트·픽스처 폴더는 제외한다. 외부 패키지(npm·pip)는 집계하지 않는다.
- **순환**(강연결 요소)의 엣지는 빨간색 "순환" 라벨로 그린다. 숨기지 않는다.
- **축소 사다리를 객관 규칙으로 적용한다**(엣지가 1.5×N 예산을 넘을 때만).
  ① **공용 모듈**: 다른 모듈의 절반 이상(3개 이상)이 의존하는 비순환 모듈은 하단 밴드로 내리고, 들어오는 엣지를 생략한다. 회색 공용 카드(`d.module(id, { shared: true })`)로 그리고, 몇 개 모듈이 쓰는지는 사이드바 설명에 적는다. 캔버스에는 숫자를 쓰지 않는다.
  ② **추이 간선**: 그래도 넘치면, 우회 경로가 있는 직접 간선을 생략한다(도달성은 보존된다).
- 생략 수는 생성된 파일 머리의 "충실도 장부"와 콘솔 출력에 남는다. 보고에 옮겨 적는다.

## 스펙 stub

```json
{ "renderer": "engine", "kind": "dependency", "view": "dependency", "title": "모듈 의존성",
  "description": "소스 모듈이 서로 무엇을 가져다 쓰는지 보여 줍니다. 여러 모듈이 함께 쓰는 공용 모듈은 맨 아래에 따로 모았습니다.",
  "source": "terra/deps.ts", "sources": ["src/**"] }
```

`sources`는 생성기가 출력하는 "sources 권장" 값을 쓴다. 코드가 바뀌어 `--status`가 stale로 짚으면 **다시 생성**한다(손으로 고치지 않는다).

## 읽는 법 (보고에 쓸 것)

- 위에서 아래로 의존한다. 아래쪽일수록 기반 모듈이다.
- 순환이 있으면 어느 모듈 쌍인지, 어떤 import 때문인지 짚는다(`--json`의 edges에 건수가 나온다).
- 레이어 규칙(예: domain이 infra를 import하면 안 됨)이 있으면 위반 엣지를 보고한다.
