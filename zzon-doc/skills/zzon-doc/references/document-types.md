# 문서 유형 판별 (그리기 전에 먼저 정한다)

> `kind`(infra/data-flow/erd/agent-topology)는 **렌더 종류**일 뿐이다.
> 그 전에 **"이건 무슨 아키텍처 문서인가"**를 판별한다. 유형이 추상화 수준·방향·중첩·배치·시각 문법을 전부 결정한다.
> 근거: C4 모델, arc42/4+1 뷰, DFD 레벨링, AWS·Azure·GCP Architecture Center 관례 조사(레퍼런스 40+).

## 판별 순서

1. **요청이 특정 유형을 지정했나?** "인프라/ERD/결제 흐름/컨텍스트" → 그 유형으로 바로.
2. **아니면 질문 두 개로 좁힌다** — ① 독자가 누구인가(비기술 포함 → 개요 계열 / 기술자 → 구조·흐름·데이터) ② 보여줄 것이 **경계·소속**인가(구조), **순서·시간**인가(흐름), **스키마·관계**인가(데이터).
3. **코드 단서로 확정한다** — 아래 표의 *단서* 열. 추측 금지, 읽은 것만.
4. **규모가 크면 유형 하나가 아니라 "추상화 사다리 세트"로 짠다** (아래 사다리 절).

## 추상화 사다리 — 큰 그림과 상세를 세트로 (핵심)

모든 방법론(C4 줌, DFD 레벨링, arc42 화이트박스)이 같은 규칙으로 수렴한다:

1. **L1 큰 그림 → L2 구조 → L3 상세의 사다리로 짠다.** 한 장에 다 넣지 않는다.
   - L1 = 시스템 컨텍스트 1장 (중심 1 + 외부만, 5~9노드)
   - L2 = 컨테이너/인프라/도메인 구조 1~2장 (10~12노드 권장)
   - L3 = 핵심 기능별 흐름 N장 + ERD + (해당 시) 배포·CI/CD
2. **한 단계 = 한 부모의 내부만 깐다.** L3 컴포넌트 장은 컨테이너 하나의 내부만. 여러 부모를 한 장에서 동시에 까면(추상화 수준 혼합) 실패다.
3. **자식 장에도 부모의 이웃을 남긴다.** 결제 흐름 장에는 호출자(웹)와 외부(PG)를 보조로 포함해 맥락을 보존한다. 이게 곧 "경계+이웃" 문법이다 — 컨테이너 장은 L1 액터·외부를, 컴포넌트 장은 L2 호출자·협력자를 경계 밖에 남긴다(sample-container·sample-component가 모범).
4. **밸런싱**: 상위 장에서 시스템에 드나들던 연결은 하위 장에서 전부 나타나야 한다(빠뜨리면 상·하위가 모순).
5. **드릴다운 연결**: 상위 장의 노드에 `href: "<하위 다이어그램 slug>"`를 달면 노드에 ⊕ 표시가 붙고, 통합 문서에서 **더블클릭으로 하위 장으로 이동**한다. 컨텍스트의 중심 시스템 → 인프라 장, 인프라의 서비스 노드 → 해당 기능 흐름 장으로 연결하라.
6. **아래로 갈수록 아껴 그린다.** L1·L2는 거의 항상 가치 있고, L3은 복잡·핵심 경로만, 코드 수준은 그리지 않는다.

## 요소 수 예산 (유형별)

- 컨텍스트: 중심 1 + 주변 **5~9** (Miller 7±2)
- 구조·흐름: **10~12** 넘으면 분할 신호. 단 종합 인프라·랜드스케이프는 크게 그리고 줌으로 봐도 된다(diagram-spec.md §6)
- 클라우드 레퍼런스 실측은 8~25 — 강조하지 않는 축은 뭉개라(AZ 3개여도 2개만, 관리형 서비스는 노드 1개)

## 조합 (큰 프로젝트의 문서 세트)

- **전형 세트**: ① 컨텍스트 1 + ② 인프라(또는 도메인 구조) 1 + ③ 기능별 흐름 N + ④ ERD 1 (+ 배포/CI/CD/에이전트).
- 세트는 `section`/`order`로 메뉴를 나눠 `build-docs.mjs`로 묶고, `href` 드릴다운으로 사다리를 연결한다.
- Azure/GCP 관례처럼 **같은 토폴로지의 관점 변주**(메인/네트워크/보안/배포)를 여러 장으로 내는 것도 정석이다.

> 유형을 골랐으면 **`diagram-spec.md`의 "레이아웃 설계 가이드 + 자가질문"**으로 배치를 점검하고 그린다.
