# 글쓰기 규칙 (독자가 읽는 글)

적용 대상은 다이어그램 제목과 요약(스펙 `description`), 사이드바에 뜨는 노드·엣지 설명, 플로우 단계 문장, 시퀀스의 설명과 메모, 위키 본문, 섹션 소개, 문서 요약, 질문 콜아웃이다.
캔버스 라벨, 코드 블록, 스펙 필드 자체는 대상이 아니다.

기준은 AWS 기술 블로그다. 한국어 블로그(aws.amazon.com/ko/blogs/tech) 6편과 Architecture·Database 블로그 3편, Well-Architected 문서 1편을 읽고 공통점을 규칙으로 옮겼다. 본보기로 삼을 만한 글은 채널코퍼레이션 DynamoDB 3부(결정을 대안과 이유로 쓴다), GS리테일 AI Gateway 2부(흐름을 번호 단계로 걷는다), API Gateway WebSocket 멀티 리전 DR(그림 한 문장 소개 뒤 요청 경로를 번호로 걷는다)이다.

다 쓰고 나면 아래 규칙으로 한 번 다시 읽는다. 엔진 품질 검사(`bun ia check`)와 위키 상태 검사(`build-wiki.mjs --status`)는 규칙 7의 추적 코드와 규칙 12의 줄표를 세어 경고한다.

## 문장

1. **본문은 합니다체로 쓴다. 제목, 캡션, 표, 목록, 캔버스 라벨은 명사형으로 쓴다.** AWS 한국어 기술 블로그는 본문을 모두 합니다체로 쓴다. 한 문서 안에서 어미를 섞지 않는다. 다이어그램 사이드바의 노드·엣지 설명도 합니다체 한 문장이다.
   - 나쁨: 주문 서비스가 큐에 넣는다. 결제는 비동기로 처리됩니다.
   - 좋음: 주문 서비스가 큐에 넣습니다. 결제는 비동기로 처리합니다.
2. **첫 문단에 무엇인지, 어떤 문제를 푸는지, 이 문서가 무엇을 다루는지를 쓴다.** 세 문장 안팎이다. "한 줄" 같은 요약 절을 따로 두지 않는다.
   - 나쁨: 본 문서는 강력하고 효율적인 주문 시스템을 소개합니다.
   - 좋음: 주문 시스템은 결제와 재고 차감을 한 번에 처리합니다. 이 문서는 요청이 들어와 확정되기까지의 경로와 실패했을 때의 동작을 설명합니다.
3. **그림은 한 문장으로 소개하고, 이어서 요청 경로를 번호 단계로 걷는다.** 번호는 그림의 순번 배지와 맞춘다. 그림을 어떻게 만들었는지는 쓰지 않는다.
   - 나쁨: 아키텍처는 아래와 같다. (그림) / C4 L1 컨텍스트 다이어그램. 노드 안에 설명을 표시한다.
   - 좋음: 그림 1은 주문 한 건이 처리되는 경로입니다. 1. 사용자가 주문을 보내면 API 게이트웨이가 인증합니다. 2. 주문 서비스가 재고를 확인합니다.
4. **단계마다 주어 하나, 동작 하나를 쓴다. 화살표 기호로 잇지 않는다.**
   - 나쁨: API → Lambda → SQS → DynamoDB
   - 좋음: API가 Lambda를 호출하고, Lambda는 메시지를 SQS에 넣습니다. 소비자가 메시지를 꺼내 DynamoDB에 저장합니다.
5. **결정은 비교한 대안, 버린 이유, 고른 이유 순서로 쓴다. 대가는 "다만"으로 시작하는 문장 하나로 같은 자리에 쓴다.**
   - 나쁨: 확장성을 고려하여 DynamoDB를 채택함(ADR-007).
   - 좋음: RDS와 DynamoDB를 비교했습니다. 쓰기가 한 사용자에게 몰리는 구조라 RDS로는 잠금 경합을 피할 수 없었습니다. 그래서 사용자별로 파티션을 나누는 DynamoDB를 골랐습니다. 다만 사용자를 가로지르는 조회는 따로 색인을 만들어야 합니다.
6. **하지 않는 일로 경계를 긋는다.** 책임을 설명할 때 무엇을 하지 않는지 한 문장을 덧붙이면 경계가 분명해진다.
   - 좋음: 코어는 유저의 실명이나 결제 정보를 받지 않습니다. 익명 식별자와 그 턴의 대화만 받습니다.

## 코드와 숫자

7. **결정 번호, 티켓 코드, 질문 번호, 절 번호를 본문 문장에 넣지 않는다.** ADR-007, FL-02, q-012, D-120, §5 같은 표기다. 그 결정이 무엇인지를 쓰고, 추적 링크는 문서 끝 "관련 자료" 절에 이름으로 모은다. 질문 콜아웃의 번호는 빌드가 쓰는 표식이라 남긴다.
   - 나쁨: OPS-1423에 따라 q-012를 반영함. 상세는 §3.2 참조(ADR-010).
   - 좋음: 장애가 나면 수동으로 전환하기로 정했습니다. (관련 자료: 이미지 워커 결정 기록)
8. **코드 식별자, 설정 키, 파일 경로, 변수 이름은 본문 문장에 넣지 않는다.** 정확한 값은 "설정 참고" 절의 표나 코드 블록에 둔다. 독자가 직접 입력하거나 검색해야 하는 이름(API 경로, ERD 문서의 테이블 이름)만 백틱으로 한 번 쓴다. 공식과 계수도 본문에 펼치지 않고, 무엇을 정하는지 한 문장으로 쓴 뒤 정본 문서로 링크한다.
   - 나쁨: `visibility_timeout=300`, `max_receive=5`로 설정하였다. 점수 `u = ln(b/90) + 0.8·avo …`로 정한다.
   - 좋음: 처리가 5분을 넘으면 메시지가 다시 보이므로, 다섯 번 실패하면 별도 큐로 옮깁니다. 답장 시각은 기분과 관계 상태에 따라 확인 창 안에서 앞뒤로 움직입니다.
9. **판단에 쓰는 숫자만 본문에 쓰고, 단위와 비교 기준을 붙인다.** 한도, 제한 시간, 목표치는 쓴다. 그림에 보이는 것을 세지 않는다. 같은 값을 문서 안에서 다르게 쓰지 않는다.
   - 나쁨: 중앙 시스템 1개와 외부 시스템 3개, 노드 6개로 이루어진다. / 성능이 대폭 개선됨.
   - 좋음: 결제 승인을 10초 안에 받지 못하면 거래를 취소합니다. 같은 트래픽에서 응답 시간이 1.6초에서 0.4초로 줄었습니다.
10. **약어는 처음 나올 때 한 번만 푼다.** 형식은 우리말 뜻(영문 약어)이다.
    - 좋음: 복구 목표 시간(RTO)을 맞추려고 시점 복구(PITR)를 켭니다.

## 피할 것

11. **과장과 빈 수식어를 빼고 사실이나 수치로 바꾼다.** 강력한, 효율적인, 혁신적인, 원활하게, 다양한, 극대화가 대상이다.
    - 나쁨: 효율적인 캐싱을 통해 강력한 성능을 제공합니다.
    - 좋음: 자주 읽는 상품 정보를 캐시에 두어 데이터베이스 조회를 70% 줄였습니다.
12. **AI가 쓴 티가 나는 문체를 피한다.** 줄표(—)로 문장을 잇지 않는다. 습관처럼 세 가지씩 나열하지 않는다. "~를 통해"를 되풀이하지 않는다. 추측을 겹치지 않는다. 괄호는 한 문장에 하나까지이고, 괄호 안에 단서를 쌓지 않는다. 문장 속 "·" 나열과 "그리고" 대신 쓰는 "+"도 쓰지 않는다. 제목 같은 짧은 명사구의 두 낱말 묶음(주문·결제)은 괜찮다.
    - 나쁨: 이 구조는 — 확장성·안정성·비용(단, 일부 예외 있음) 측면에서 — 유연한 대응을 가능하게 할 수 있습니다.
    - 좋음: 트래픽이 늘면 소비자 수만 늘리면 됩니다. 다만 순서가 중요한 메시지는 한 소비자가 처리해야 합니다.
13. **목록은 단계, 전제 조건, 참고 자료에만 쓴다.** 설명과 이유는 줄글로 쓴다. 표 칸에 문단을 넣지 않는다. 표 칸은 한 문장까지다.
    - 나쁨: 결정 이유를 "확장성 · 비용 · 운영 편의" 같은 낱말 목록으로 적는다.
    - 좋음: 이유 하나를 한 문단으로 풀어 씁니다.
14. **짧게 쓴다.** 그림과 문서 요약은 한두 문장, 노드·엣지 설명과 플로우 단계는 한 문장이다. 다른 그림을 가리키는 말은 링크나 드릴다운에 맡긴다.

관계 표기처럼 기호가 곧 정보인 내용은 그림이나 표에 맡기고, 문장으로는 뜻을 쓴다.
- 나쁨: `users 1 — 0..N orders`
- 좋음: 회원 한 명이 주문을 여러 건 가질 수 있고, 주문이 없는 회원도 있습니다.

## 문서 틀 (아키텍처·설계 문서)

절 이름은 문서 성격에 맞게 바꿔도 되지만 순서는 지킨다. 해당 없는 절은 빼도 된다.

1. **개요**: 무엇인지, 어떤 문제를 푸는지, 이 문서의 범위를 세 문장 안팎으로 쓴다.
2. **배경과 요구 사항**: 제약과 목표를 쓴다. 수치 목표가 있으면 여기에 둔다.
3. **아키텍처**: 그림 한 장과 소개 문장을 넣는다. 구성 요소마다 하위 제목을 두고, 하위 제목 순서를 데이터가 흐르는 순서와 맞춘다.
4. **동작 흐름**: 대표 경로 한두 개를 번호 단계로 걷는다. 실패 경로를 따로 둔다.
5. **설계 결정**: 결정마다 대안, 버린 이유, 고른 이유, 대가를 쓴다. 대안이 셋 이상이면 비교를 표로 둔다.
6. **고려 사항과 한계**: "다만" 문장과 아직 검증하지 않은 것을 쓴다.
7. **설정 참고**: 표와 코드 블록에 정확한 값을 둔다. 문서에서 변수 이름이 나오는 곳은 여기뿐이다.
8. **관련 자료**: 정본 문서, 결정 기록, 티켓으로 가는 링크를 이름으로 둔다. 추적 번호는 여기에만 쓴다.

운영 런북은 장애 유형마다 증상, 확인, 조치, 되돌리기 순서로 쓴다. 용어 사전은 용어마다 한 문장 정의와 쓰이는 곳을 쓴다.

## 그림의 글

- 제목은 무엇을 보여 주는지를 명사구로 쓴다. 추적 코드와 C4 레벨 코드를 넣지 않는다(나쁨: "채팅 1턴 (FL-02)", 좋음: "메시지 한 번 주고받기").
- 노드 라벨은 이름, 보조 줄(sublabel)은 기술이나 역할 한두 낱말이다. 설명 문장은 `description:`에만 쓴다.
- 선 라벨은 2어절 안쪽이다. 테이블·컬럼 이름이 꼭 필요하면 선 설명으로 옮긴다.
- 선 종류(레이어) 이름은 범례에 그대로 보이므로 한국어로 쓴다(나쁨: metric, notify / 좋음: 지표, 알림).
- 시퀀스 메시지 라벨은 짧은 한국어 동작으로 쓰고, 요청 본문과 SQL은 단계 설명으로 옮긴다(나쁨: `POST /v1/messages { client_message_id, body }`, 좋음: "메시지 전송").
