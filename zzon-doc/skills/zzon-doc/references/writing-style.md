# 글쓰기 규칙 (독자가 읽는 글)

적용 대상은 다이어그램 제목과 요약(스펙 `description`), 사이드바에 뜨는 노드·엣지 설명, 플로우 단계 문장, 시퀀스의 설명과 메모, 위키 본문, 섹션 소개, 문서 요약, 질문 콜아웃이다.
캔버스 라벨, 코드 블록, 스펙 필드 자체는 대상이 아니다. 다 쓰고 나면 아래 여섯 가지로 한 번 다시 읽는다.

1. **사람에게 설명하듯 한다체 문장으로 쓴다.** 시스템이 무엇이고 어떻게 움직이는지를 쓰고, 그림을 어떻게 만들었는지는 쓰지 않는다. 조작 안내는 독자가 눌러야 할 것이 있을 때만 한다.
   - 나쁨: C4 L1 컨텍스트 다이어그램. 노드 안에 설명을 표시한다(nodeDescriptions).
   - 좋음: 데모숍을 누가 쓰고 어떤 외부 서비스에 기대는지 보여 준다. 데모숍을 더블클릭하면 내부 구성 그림으로 넘어간다.
2. **코드 식별자, 스펙 필드 이름, 파일 경로, 설정 키를 문장에 넣지 않는다.** 독자가 직접 입력하거나 검색해야 하는 이름(API 경로, ERD 문서의 테이블 이름, 환경 변수)만 쓴다. 위키 본문에서는 그 이름을 백틱으로 감싸고 한 번만 쓴다.
   - 나쁨: hints.layer로 열을 고정했다. 근거는 services/order/** 이다.
   - 좋음: 주문 서비스는 결제 승인을 받은 뒤에만 주문을 확정한다.
3. **내부 코드와 분류 기호를 쓰지 않는다.** 등급 코드(T1, T2, T3), C4 레벨 코드(L1, L2), 질문 번호(q-001), 섹션 번호, 뷰 slug는 말로 풀거나 뺀다. 질문 콜아웃의 번호는 빌드가 쓰는 표식이라 남기되 본문 문장에는 쓰지 않는다.
   - 나쁨: L2 컨테이너 장(T2)에서 이어지며, q-003 답변 후 갱신한다.
   - 좋음: 시스템 내부 구성 그림에서 이어진다. 결제대행사 연동 범위가 확정되면 고친다.
4. **기호를 문법 대신 쓰지 않는다.** 화살표 사슬(A → B → C), 문장 속 "·" 나열, "그리고" 대신 쓰는 "+", 줄표(—)로 끼워 넣는 말, `1 — 0..N` 같은 표기를 문장에 쓰지 않는다. 괄호는 한 문장에 하나까지다. 단계가 이어지면 문장이나 짧은 목록으로 쓴다. 제목처럼 짧은 명사구의 두 낱말 묶음(주문·결제)은 괜찮다.
   - 나쁨: 좌→우가 요청의 흐름이다: 사용자 → 엣지(CDN·WAF) → 게이트웨이 → 도메인 → 데이터.
   - 좋음: 요청은 왼쪽에서 오른쪽으로 흐른다. CDN과 웹 방화벽을 지나 게이트웨이에 닿고, 도메인 서비스가 처리해 저장소에 기록한다.
5. **숫자는 독자에게 필요한 정보일 때만 쓴다.** 한도, 제한 시간, 목표치, 판단에 쓰는 개수는 쓴다. 그림에 보이는 것을 세지 않는다.
   - 나쁨: 중앙 시스템 1개와 외부 시스템 3개, 노드 6개로 이루어진다.
   - 좋음: 결제 승인을 10초 안에 받지 못하면 거래를 취소한다.
6. **짧게 쓴다.** 그림과 문서 요약은 한두 문장, 노드·엣지 설명과 플로우 단계는 한 문장이다. 다른 그림을 가리키는 말은 링크나 드릴다운에 맡긴다.
   - 나쁨: 주문 생성·결제 오케스트레이션. 내부는 컴포넌트 장 참조. 스키마는 ERD 장 참조.
   - 좋음: 주문을 만들고 결제 승인까지 조율한다.

관계 표기처럼 기호가 곧 정보인 내용은 그림이나 표에 맡기고, 문장으로는 뜻을 쓴다.
- 나쁨: `users 1 — 0..N orders`
- 좋음: `users`와 `orders`: 회원 한 명이 주문을 여러 건 가질 수 있고, 주문이 없는 회원도 있다.
