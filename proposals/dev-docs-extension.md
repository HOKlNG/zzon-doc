## 무엇을 하려는가

"개발 문서 정리해 줘"라는 요청에 화면, 디자인, 기능 추적까지 갖춘 문서 세트를 내놓는다. 지금 zzon-wiki 카탈로그는 아키텍처와 데이터는 촘촘하지만 화면과 디자인 쪽은 슬롯 이름만 있다. 실제 운영 중인 프로젝트(estel)의 문서 구조에서 **틀만** 가져와 일반화한다. 내용은 가져오지 않는다. 모범 문서는 가상의 데모숍으로 쓴다.

이 문서는 제안이다. 아직 스킬에 반영하지 않았다. 함께 만든 예시 위키에서 각 문서가 어떻게 보이는지 확인할 수 있다.

## 새로 들어갈 문서

| 섹션 | 문서 | 언제 나오나 | 담는 것 | 미리 채우는 것 | 그림 |
|---|---|---|---|---|---|
| 기획 | 기능 목록 | 기능이 3개 이상이거나 전체 문서 세트일 때 | 기능 ID, 이름, 출시 단계, 상태, 연결된 화면과 API | 라우트·API 목록에서 기능 후보 | 없음 |
| 기획 | 핵심 흐름 | 왕복이나 분기가 있는 사용자 흐름이 있을 때 | 흐름마다 목적, 시작 조건, 단계, 예외 | 없음 | 시퀀스 또는 플로우차트 |
| 화면 설계 | 정보 구조(IA) | 화면이 3개 이상일 때 | 읽는 법과 정본, 앱 구조, 화면 사이 이동, 화면 목록, 라우트가 아닌 화면 | 라우트 파일에서 화면 목록과 종류(탭·스택·모달) | 라우트 트리(앱 시작 분기, 영역별 화면 썸네일, 바깥에서 들어오는 길), 화면 흐름 |
| 화면 설계 | 화면 설계 | 화면이 3개 이상일 때. 화면마다 하위 문서 | 와이어프레임과 명세(목적, 블록, 액션, 상태, 이동), 화면별 데이터·엣지 규칙·접근성 | 화면 파일이 부르는 API, 화면 파일의 주요 컴포넌트 | 화면 와이어프레임(전체, 화면 한 장) |
| 화면 설계 | 스토리보드 | 화면이 8개 이상이거나 요청할 때 | 흐름별 프레임(화면과 누르는 곳), 공통 컴포넌트, 결정 대기 | 없음 | 흐름별 프레임 |
| 화면 설계 | 디자인 시스템 | 테마나 토큰 파일이 있을 때 | 원칙, 색, 서체, 간격과 형태, 모션, 상태 어휘, 컴포넌트, 접근성, 토큰 코드 | 토큰 파일 위치와 값 | 토큰 시각판 |
| 아키텍처 | 하위 시스템 | 배포 단위 2개 이상이거나 모듈 5개 이상일 때. 서비스마다 하위 문서 | 책임, 경계, 데이터, 인터페이스, 장애 시 동작, 관측 | 모듈의 공개 진입점 | 상태 전이, 컴포넌트 |
| 데이터 | 개인정보·규제 | 개인정보 컬럼이나 동의·연령 확인 코드가 있을 때 | 수집 항목과 근거, 보존과 삭제, 동의 흐름, 열람·삭제 요청 처리 | 개인정보 후보 컬럼 | 플로우차트(동의 흐름) |
| 운영 | 비용 | IaC가 있을 때 | 리소스별 월 비용 추정, 비용이 늘어나는 요인, 줄일 여지 | IaC 리소스 목록 | 없음 |

지금 있는 디자인 섹션의 노출 규칙도 바꾼다. 지금은 가장 큰 티어에서만 나오고, Figma를 쓰면 섹션 전체가 빠진다. 바꾼 뒤에는 화면이 있으면 IA와 화면 설계가 표준 티어로 나온다. Figma를 써도 이 둘은 남긴다. Figma에는 라우트, 데이터, 상태 규칙이 없기 때문이다. 디자인 시스템만 "Figma가 정본"이면 링크 한 줄로 대신한다.

## 문서 틀

새 문서는 빈 종이에서 시작하지 않는다. `references/doc-skeletons/`에 문서 종류별 틀을 두고, 스킬은 틀의 절을 채운다. 해당 없는 절은 지우지 않고 "해당 없음"과 이유를 한 줄로 적는다. 독자가 무엇이 빠졌는지 알 수 있어야 한다.

| 틀 | 절 |
|---|---|
| 정보 구조 | 어떻게 읽나(정본 문서 링크) · 앱 구조(라우트 트리) · 화면 사이 이동(화면 흐름) · 화면 목록(영역, 라우트, 이름, 유저가 끝내려는 일, 기능) · 라우트가 아닌 화면(시트·다이얼로그) |
| 화면 설계 | 와이어프레임 · 목적 · 진입과 이탈 · 데이터(표시, 출처, 갱신 시점) · 상태(로딩, 빈, 오류, 오프라인, 권한 없음, 잠금) · 액션(API, 낙관적 갱신, 실패 시) · 엣지 규칙 · 접근성과 다국어 |
| 스토리보드 | 어떻게 읽나 · 흐름별 프레임 · 공통 컴포넌트 · 디자인 결정 대기 |
| 디자인 시스템 | 원칙 · 색 · 서체 · 간격·형태·깊이 · 모션 · 상태 어휘 · 컴포넌트 · 접근성 · 토큰 코드(값이 한 곳에서만 나오는 구조) |
| 기능 목록 | 단계 정의 · 기능 표(ID, 이름, 단계, 상태, 화면, API) · 연결이 빠진 기능 |
| 핵심 흐름 | 흐름마다: 목적 · 시작 조건 · 단계 · 예외 · 관련 화면 |
| 하위 시스템 | 책임 · 경계(하지 않는 일) · 데이터 · 인터페이스 · 장애 시 동작 · 관측 |
| 개인정보·규제 | 수집 항목과 근거 · 보존·삭제 · 동의 흐름 · 열람·삭제 요청 처리 |
| 비용 | 월 비용 추정 · 비용이 늘어나는 요인 · 줄일 여지 · 가정 |

## 화면 정의 파일

IA, 화면 설계, 스토리보드의 그림은 모두 화면 정의 파일 하나(`screens.json`)에서 만든다. 같은 화면을 세 문서가 따로 그리지 않는다.

| 항목 | 담는 것 |
|---|---|
| 영역 | 로그인 전, 탭, 스택, 시트처럼 화면을 묶는 단위와 한 줄 설명 |
| 화면 | 라우트, 이름, 기능 ID, 목적, 블록 목록, 액션·상태·이동, 시트라면 열리는 부모 화면 |
| 앱 시작 | 앱을 열 때 확인하는 것과 갈래별 도착 화면 |
| 바깥 진입 | 딥링크, 푸시 같은 바깥에서 들어오는 길과 규칙 |
| 흐름 | 단계마다 화면과 누르는 블록 |

블록은 정해진 어휘로 쓴다: 상단 막대, 검색창, 배너, 상품 격자, 목록, 상품 줄, 행, 합계, 버튼, 바닥 버튼, 칩, 사진, 가격, 단계 표시, 프로필, 안내 문구, 탭 바, 시트. 렌더러는 이 어휘로 회색조 폰 프레임을 그린다. 실제 색과 모양은 디자인 시스템이 정하므로 와이어프레임은 배치만 보인다. 명세 표의 블록 줄은 블록 목록에서 뽑으므로 손으로 따로 쓰지 않는다.

이 파일은 코드에서 미리 채운다. 라우트 파일에서 화면과 영역을, 화면 파일의 주요 컴포넌트에서 블록 후보를 뽑고, 사람이 확인해 고친다.

## 공통 규칙

- **정본은 하나다.** 같은 사실은 한 문서에만 쓰고 다른 문서는 링크한다. 예를 들어 라우트 목록의 정본은 IA, 색 값의 정본은 토큰 파일이다.
- **기능 ID는 표와 링크에서만 쓴다.** 기능 목록에서 ID를 정하고(예: 주문 O1, 결제 P2), 다른 문서의 표에서 그 ID로 기능을 가리킨다. 본문 문장에는 기능 이름을 쓴다. 문체 규칙의 "내부 코드를 글에 쓰지 않는다"에 대한 예외로 명시한다.
- **결정 대기는 질문 대장으로.** 미정인 디자인 결정은 기존 질문 대장(❓ 콜아웃)으로 남긴다. 위키 진행 현황에 모인다.
- **그림은 zzon-doc 메인 절차로.** 화면 사이 이동은 화면 흐름 뷰에 열 규칙(진입, 로그인 전과 탭, 스택, 시트)을 적용하고, 큰 그림과 세부 판단도 똑같이 따른다.
- **문서형 그림은 글처럼 흐른다.** 와이어프레임, 라우트 트리, 스토리보드, 토큰 시각판은 캔버스가 아니라 화면 폭에 맞춰 다시 배치되는 페이지다. 넓은 화면에서는 와이어프레임과 명세가 나란히, 휴대폰에서는 위아래로 놓인다.

## zzon-doc에 필요한 것

| 기능 | 설명 |
|---|---|
| 라우트 추출 | 스캐너가 라우트 파일(Next.js app·pages, Expo Router, React Router, Flutter 라우트)에서 경로와 종류(탭, 스택, 모달)를 뽑아 IA 화면 목록을 미리 채운다 |
| 토큰 추출 | 테마·토큰 파일(Tailwind 설정, CSS 변수, tokens.json, theme.ts)을 찾아 값을 읽는다 |
| 토큰 시각판 | 토큰 값에서 색 견본, 서체 단계, 간격 눈금, 컴포넌트 미리보기를 담은 단일 HTML을 만든다. 위키에 다이어그램처럼 넣는다 |
| 화면 렌더러 | 화면 정의 파일에서 와이어프레임(전체, 화면 한 장), 라우트 트리, 흐름별 프레임을 단일 HTML로 만든다. 외부 의존 없이 폰 프레임과 블록을 CSS로 그린다 |
| 화면 정의 미리 채우기 | 라우트 추출 결과와 화면 파일의 컴포넌트 이름으로 `screens.json` 초안을 만든다 |
| IA 구조 배치 | 화면 흐름 뷰 가이드에 앱 구조도 열 규칙을 넣는다 |
| 개인정보 후보 | 스캐너가 이메일, 전화, 생년월일, 주소 같은 이름의 컬럼을 개인정보 후보로 센다 |

## 위키 셸에 필요한 것

- 기능 ID를 기능 목록의 해당 행으로 자동 링크한다.
- 진행 현황 페이지에 "화면이나 API와 연결되지 않은 기능"을 보여 준다.
- 화면 설계 하위 문서 카드에 화면 종류(탭, 스택, 시트)를 표시한다.
- 문서형 그림이 알려 오는 높이로 임베드 창을 맞춘다. 이 부분은 반응형 수정으로 이미 넣었다(`zzon:height` 메시지).

## 도입 순서

1. 문서 틀, 카탈로그 슬롯, 질문 은행, 노출 규칙. 코드 변경이 거의 없다.
2. 화면 정의 파일 스키마와 화면 렌더러. IA, 화면 설계, 스토리보드에 화면이 들어간다.
3. 라우트·토큰 추출과 화면 정의 미리 채우기.
4. 토큰 시각판 렌더러.
5. 기능 ID 링크와 연결 누락 경고.
6. 비용과 개인정보 문서의 미리 채우기.

## 예시 위키에서 볼 것

- **기능 목록:** 기능 ID가 IA와 화면 설계 표에 어떻게 이어지는지
- **정보 구조:** 앱 시작 분기, 영역별 라우트 트리(화면 썸네일), 바깥에서 들어오는 길, 화면 사이 이동
- **화면 설계:** 화면 11개의 와이어프레임과 명세, 화면별 문서(상품 상세, 장바구니)의 와이어프레임
- **스토리보드:** 첫 구매 다섯 프레임과 누르는 곳 번호, 결정 대기
- **디자인 시스템:** 토큰 시각판이 문서 안에 들어간 모습
- **하위 시스템, 개인정보·규제, 비용:** 각 틀의 실제 모습
